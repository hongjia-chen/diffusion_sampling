Why remasking fixed about as many answers as it broke

A dissection of the 1,500 paired task runs (3 benchmarks × 5 δ × 100 tasks) against the exact no-remask counterfactual, the 75 traced tasks, and a new offline Dream probe on GSM8K's arithmetic slips.

Short answer

The remask pass looks for the lowest Dream probability in a finished block. That score mostly measures style mismatch between the two models, not error. The pass is also structurally unable to repair the errors SDAR actually makes. The one-token edit then perturbs SDAR's next blocks, and that re-generation decides the outcome. The net is noise with a slight positive tilt:

  1. The detector aims at style. On GSM8K, 89% of first edits hit canvas position 0 and just remove a leading space ( If→If). On MBPP+, the most common edit is a line-ending swap (\r\n→\n).
  2. Hindsight hides real errors. The pass scores each token with the rest of the block visible. By then SDAR has built on its mistakes. 81–90% of tokens Dream found improbable at commit time look fine once the block is complete. For real arithmetic slips, Dream flags 71% from the prefix and suggests the correct digit in 67%. In the remask pass's view it endorses 57% of them.
  3. The edit can't express the fix. Qwen tokenizes numbers digit by digit, and substitution can't insert or delete. 69% of GSM8K slips change the number's length, and 94% are reused later in the answer. On code, renaming a variable at one site breaks every other use of it.
  4. The rest of the answer decides. Twelve identical edits fixed the task at one δ and broke it at another. Flips are 3–9× more common on tasks that are already unstable without remasking.
  5. The verifier never adds Dream's own answer. With no veto, the Dream-only ratio only sets how many of SDAR's tokens to commit, never which. Quality is capped at SDAR greedy (0.80 vs cross 0.81 on GSM8K). Dream's knowledge can enter only through one token per 64.

The latency cost is mostly the verifier, not remasking: the remask pass is 21–39% of Dream rows. The whole method is 5–14× slower than SDAR fixed:1 at about the same accuracy.

3 · Five reasons

What the data says is going on

A

The lowest-probability token is a style mismatch, not an error

The pass picks from the 4 tokens Dream finds least likely. Dream is a different model with a different house style (Qwen2.5-based, EOS <|endoftext|>, and evidently no leading space on the first answer token). So its least-likely tokens are mostly where SDAR's style differs. SDAR's first answer token carries a leading space, which Dream scores at about log p ≈ −9 to −11. That is lower than almost any real error, and the 1/p draw then picks it hundreds of times more often than anything else.

439 / 495GSM8K first edits land on canvas position 0
369 / 495are whitespace-only: If→If (113×), The→The (61×)…
23MBPP+ first edits are ):\r\n→):\n
81HumanEval+ first edits sit in the prose explanation, which evalplus never runs

A cosmetic edit alone rarely flips a score (3 of 129 runs whose only edit was cosmetic). But on GSM8K it uses up block 0's single remask, and most answers have only 2–3 blocks. In one probe case (gsm8k-test-991, 30 + 75 = 220), the wrong digit was in the bottom 4. The position-0 space outweighed it by about 400:1.

B

Leave-one-out in hindsight rationalizes propagated errors

The pass runs after the block is complete, with every other token visible. By then SDAR has written the rest of the block conditioned on each earlier token, so a wrong token is surrounded by text that agrees with it. Dream's bidirectional view reads that agreement as evidence. Across the traced passes:

81–90%of tokens Dream gave p < 0.1 at commit time have p > 0.1 by the remask pass
+3.4 to +4.2nats median gain for those tokens (30–60× more probable in hindsight)

The same wrong digit that Dream rejects at p ≈ 0.004 and corrects 2 times in 3 when it can't see what follows looks almost certain (p ≈ 0.99) once SDAR's continuation is visible. gsm8k-test-601 48 + 15 = 5: log p −1.25 from the prefix, −0.0003 in the remask view. gsm8k-test-602 1200/3 = 4000: the extra zero scores −10.1 from the prefix and −0.003 in the remask view.

"Prefix only" masks the slip digit and everything after it. It approximates the commit-time view, where SDAR's confidence ordering may already have committed a few later tokens. Pick chance assumes all bottom-4 tokens survive the argmax filter and applies the 1/p draw.

C

One in-place token substitution can't express the fix

SDAR's GSM8K errors are mostly not token-local. Of the 142 wrong no-remask answers, 62% contain no detectable arithmetic slip: the plan is wrong, and no single token repairs a plan. The remaining 38% contain an explicit slip, but the edit operator can't fix most of those either:

35 / 51slips change the number's length (1200/3 = 4000), which needs an insert or delete
12 / 51are a single-digit substitution. Numbers are tokenized one digit at a time.
48 / 51reuse the wrong value later, so fixing the slip alone doesn't fix the final answer

On code, the edits are meaningful: >→ ==, a missing ]) restored at the stop. But renaming an identifier at one site ( sum→ total, (lst→(nums, roman→ mapping) leaves every other use pointing at a name that no longer exists. That is the main way remasking breaks correct code.

D

SDAR's re-generation decides the outcome, not the edit

After the edit, SDAR writes the edited block into its KV cache and decodes every later block from the new context. The median similarity of the text after the edit is 0.89 on GSM8K and 0.75–0.78 on code. Whether the answer ends up right depends on that re-generation:

So remasking mostly shakes borderline tasks. It is closer to "draw another sample" than "correct the mistake". That also explains why P(fix | wrong) is high on GSM8K (0.28): about a quarter of its wrong answers are borderline.

E

The verifier never adds Dream's own tokens, so the ceiling is SDAR's

The acceptance test |Σ log pD(y|c,y<j) − log pD(y|c)| ≤ log(1+δ) checks whether proposals depend on each other, not whether Dream agrees with them. With the veto off, the first candidate is always committed. At commit time, SDAR's top token differed from Dream's argmax on 14–22% of steps (about 2 per block), and 3–7% of committed tokens had Dream p < 0.1. All of them went in. Remasking later gets one of them back per block, and by then B has hidden most of them.

4 · What to try next

Ideas, roughly in order of evidence per GPU-hour

Stop spending the budget on style

cheap · no new forwards

Treat whitespace/case/CRLF variants as one symbol, the same way the stop set already is (remask_pass's same_stop). At minimum, skip canvas position 0. That frees about one third of GSM8K's remask budget. It is the smallest change and a clean test of cause A.

Prevent instead of cure: turn the veto on, or veto on low Dream probability

free · row 0 already computed

At commit time Dream still disagrees about 2× per block, and nothing has been built on the token yet. Committing Dream's argmax there (--veto, already implemented) targets the moment before B hides the error. Generalize it to any accepted position with pD < τ. This is the only lever that lets Dream's own answer in at more than 1/64.

Rank suspects by commit-time probability, not hindsight

cheap · the deferred shortlist

DESIGN.md deferred the qi shortlist, fearing it would miss tokens that "only look wrong in hindsight". The data points the other way: hindsight makes tokens look right. Use qi, or the hindsight gain LOO − qi, to shortlist 8 and re-score only those. That cuts remask cost about 8× and should aim better. The probe in B supports this: the prefix view flags 71% of real slips, while the remask pass would pick one only about 14% of the time.

Remask a span, then re-decode it

moderate

When a token is flagged, remask it and the rest of the block after it (or the whole number / all uses of the identifier) and let SDAR or Dream re-decode. That allows length-changing fixes (4000→400), multi-digit fixes, and consistent renames. It also removes the "stale downstream" that makes hindsight scoring self-confirming.

Only let edits land where the scorer looks

cheap

For code, restrict remasking to inside the fenced block. 81 HumanEval+ first edits were in prose, where any effect is pure perturbation. Also forbid edits to identifier tokens, or rename all occurrences together.

Measure against the right null

analysis

Before the next sweep, add a random-edit control: same budget, random position, Dream's argmax. If it flips as many tasks as the 1/p rule, the detector adds nothing. Report McNemar per benchmark instead of pooled accuracy deltas, since ±2–4 points on 100 tasks is within noise.
